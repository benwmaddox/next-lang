# LangArena ports

Ports of the 50 [LangArena](https://github.com/kostya/LangArena) tests (MIT; see LICENSE-LangArena), the self-hosted compiler's acceptance target (docs/PLAN.md). `run.js` and `test.js` are LangArena's parameter files, vendored unchanged; each entry's `checksum` is the expected output.

Conventions, one directory per test, named after the test in lowercase with `::` as `_` (`Binarytrees::Obj` -> `binarytrees_obj/`):

- `name`: the LangArena test name, one line.
- `main.nl` and `package.toml` (`capabilities = ["env", "out"]`): the program. Its first argument is the mode, `test` (small parameters from test.js) or `run` (full parameters from run.js); `env.args().get(0L)` is that argument (see `_skeleton/`). Its second argument may be `prep`, which performs only preparation and warmup and prints an unverified checksum state. The normal mode prints the checksum as one decimal line, last.
- `status` (optional): `pending-floats` (needs floats, step F1), `pending-threads`, `pending-regex`, or `pending-<reason>` while it can't be checked yet; absent means ready.
- The algorithm follows LangArena's reference implementations (rust/src/benchmarks/*.rs is a good source) closely enough that the checksum matches, written idiomatically for next-lang: bounded collections with capacities large enough for the run parameters, `write` parameters, pools and typed ids instead of pointers, no mutable globals, no name shadowing.

Check: `python3 bench/langarena/check.py --mode test` (and `--mode run --time`) builds every package with the self-hosted compiler (clang -O3, C runtime) and compares the output with the checksum.

## Fair comparison conventions

The goal is a like-for-like comparison with LangArena's own implementations (Crystal is the original reference, Rust a cross-check): the same algorithm, the same data-structure shape (objects with neighbour lists stay objects with lists, per-node allocation stays per-node allocation, precomputed stays precomputed), the same work and parameters. Each package has an `audit` file with its verdict against the Crystal reference (`like-for-like`, `rewritten-to-match`, or `closest-possible` with what still differs and why). Only `like-for-like` and `rewritten-to-match` packages appear in the headline geometric mean; known `closest-possible` differences are shown separately.

- **Prep mode.** LangArena times only `run_all()`, after `prepare()` and `warmup()` (max(0.2 * iterations, 1) untimed runs, or `warmup_iterations`). `run prep` / `test prep` performs only preparation and warmup, then prints an unverified checksum state. The normal mode runs preparation, warmup and timed iterations. `compare-rust.py` estimates next-lang run-body time by subtracting the best whole-process `run prep` time from the best whole-process `run` time. Since these are separate process measurements, the result includes timing noise and is not an in-process measurement. The whole-process `run` time is an extra column. Memory is the peak RSS of the `run` process on both sides.
- **Variants.** A port that had to be rewritten to match the reference keeps its earlier, more idiomatic next-lang version as `<test>_idiomatic/` (same `name`, `status` = `variant-idiomatic`). Variants are built, checked and reported in a separate section, never in the headline numbers.
- **Not comparable.** `status` = `not-comparable: <reason>` marks ecosystem tests where LangArena's reference uses a library (regex, JSON, CSV...) and our port hand-writes a substitute. They are built and checked, and reported separately, not in the headline geometric mean. Hand-written base64 stays like-for-like (the Rust reference uses the base64-simd crate, Crystal its stdlib).
- `check.py` also runs `<mode> prep` for every buildable package and requires exactly one decimal line. Because a valid prep checksum can equal the full-run checksum when the timed loop's contribution is zero, the harness checks its output shape and exit status; source review confirms that the prep path stops after warmup. `compare-rust.py` verifies the next-lang checksum and exit status in every measured run, checks the prep output shape and that the Rust runner completed successfully, and exits nonzero when a build or measurement fails.
