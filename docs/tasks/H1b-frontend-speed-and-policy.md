# H1b: a fast self-hosted front end and one input policy

**Status (2026-10-25):** the compilers were split (docs/PLAN.md, Order of work item 3). Only item 1 (one input policy for all commands) is still to be done, as a small task; items 2 to 4 (front-end speed through nlc) are dropped.

Depends on H1. Read docs/tasks/H1-report.md, docs/reviews/claude-H1-review.md and docs/tree-binary-format.md.

1. **One input policy for both front ends and both commands** (decided by Claude as manager 2026-10-25, under "one approach at a time"; Ben may overrule): `nlc run/build/test` apply the same package limits `nlc parse` applies today (256 files, 16 MiB per file, 64 MiB per package, 1,000,000 tokens per file, 4,000,000 per package, 2,000,000 nodes, the work limit, nesting 1,000), with the same messages and order, in the Rust and the self-hosted front ends alike. Invalid UTF-8 is a syntax diagnostic (status 2) in every command. Update docs/syntax-tree-format.md's command section and DESIGN where it describes compile inputs; tests for each limit at N and N+1 under both front ends and commands. The self-hosted front end's storage then needs exactly these limits (lower its 4,096-file and +1 capacities to the policy).
2. **Measure in release first:** H1's numbers came from the debug nlc. Build nlc with `cargo build --release` (a separate CARGO_TARGET_DIR if needed) and report, for the benchmark and for a small package, the time of each stage on both front ends: Rust lex and parse; for the self-hosted path, the cache check, child start, the child's parse, writing the tree, transport, reading and validating, and rebuilding the AST. All later targets are measured with release nlc.
3. **Per-call overhead:** profile the ~250 ms fixed cost per call (cache-key computation, child startup and stack reservation, temp file handling) and remove it: compute the expensive parts of the cache key once per nlc build (a build id embedded at compile time, the runtime and selfhost sources hashed once and recorded with the cached artifact, checked by size and modification time first), avoid re-hashing on every call. Target: a small package within 15% of the Rust front end (release nlc, best of 5).
4. **Wire size and reading:** make the format compact (variable-length integers, spans as deltas from the parent or previous sibling, no duplicated data the reader can derive), stream it through a pipe instead of a temporary file if that's faster, and rebuild the AST in one pass, validating while rebuilding (not in separate passes), with AST nodes allocated in bulk rather than one heap allocation each, and without holding the whole wire and the AST plus copies at once. Bump the wire version. Targets: about 5 bytes of wire per source byte on the benchmark (8 at most), parent peak memory within 1.15 times the Rust front end's, and the benchmark within 15% of the Rust front end end to end (release nlc, best of 5). If a target can't be met across a process boundary, report how close it gets and which stage is left; that's H1c's input.
5. Keep differential AST equality and both full suites passing; rerun H1's malformed-wire and cache tests.
- Report: docs/tasks/H1b-report.md, with before/after numbers and a recommendation on the default.
