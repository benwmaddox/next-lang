# Review 4: `docs/DESIGN.md`

## 1. Round-3 fixes still needing correction

1. **The worked example still cannot establish its bounds.** *How the compiler assigns stacks; Loops can't quietly fill a stack.* Unicode uppercasing can expand text: 60 copies of `ß` become 120 code points under full uppercase mapping, before punctuation or digits. Thus neither `line: Text max 80` nor the claimed scratch bound follows from `name max 60`. Use an explicitly ASCII-only uppercase helper, or give `upper` a sound output-length contract and recompute all dependent bounds. Also, `List<Row>` contains variable-length text, which the new nested-growing-value restriction refuses on stacks. Make `rows` and `r` explicit read-only views into table storage; otherwise the example requires the deferred representation. [Unicode case-mapping FAQ](https://www.unicode.org/faq/casemap_charprop.html)

2. **The batch-race fix is absent from the cleanup checklist.** *Thread kinds and jobs / Batch states; Types / What failing a job does.* The former requires acknowledgement from an applying batch before freeing its input buffers. Cleanup step 3 covers unsent, queued and committed batches but omits that wait. Add: cancel queued batches; for an applying batch, wait for the writer to acknowledge either abort or commit before releasing memory; preserve any commit. The checklist must be safe when implemented on its own.

3. **The join and cancellation fixes leave contradictory summaries.** *Tables across threads / Slow readers; Types / failure step 2.* Slow readers still says pins span only computing with “no waits,” despite the parallel-join exception. Failure cleanup still describes cancellation checks only at step-budget checks, despite counted loops omitting those budgets. Refer explicitly to structured joins and to cancellation polls in both kinds of loop. Their memory and deadline guarantees depend on those exceptions being implemented consistently.

## 2. Most important remaining problems

1. **Choose the slot-storage rule before step 1.** *Memory / Typed ids; First steps.* A slot number is not necessarily a physical row number: deleting a row and moving the last row into its place would silently change which record another id names. For the first implementation, use slot-indexed columns with holes, plus occupied flags, generations and a free-slot list. Check slot bounds, occupancy and generation before reading fields. Snapshot the flags and generations with the columns when snapshots arrive. If dense storage is wanted later, add an explicit slot-to-row map. Verify deletion, reuse, stale lookup and generation retirement.

2. **Owned copies and result placement need a fallback contract.** *Memory / References; How the compiler assigns stacks / Fresh result; Loops / reassignment.* Returning a read-only text parameter as an owned `Text` necessarily copies its bytes; passing a destination does not remove that copy. Likewise, `let b = a` must say whether it copies or consumes `a`. Specify copies for ordinary growing-value assignment, with any ownership transfer explicit. Build directly into a destination only when the compiler proves that placement safe; otherwise copy from scratch and count both live values. Keep fresh-result and append destinations in the overlap check, and qualify the blanket “returning ... is no copy” claim. Step 2 needs examples for returning an input, returning a local previously read, and replacing an accumulator.

3. **Private-table views need mutation rules.** *Memory / References and job-owned tables; Frozen tables / Build.* Snapshot views have pinned storage, but private tables and builders use mutable arrays. Adding rows can relocate an array; replacing a payload or deleting a row can invalidate a view even on one thread. Define a view's owner as the underlying table storage, not merely the row's logical id. Initially reject structural mutation while a view of that table is live; end the borrow before insertion, deletion, payload replacement or compaction. Allow narrower exceptions only where stable storage proves them safe. Include these rules when table views enter the first implementation.

4. **Writer transactions need staged state and an execution boundary.** *Thread kinds and jobs / Transactions, Reads; Memory / SQLite queries.* Running checks on the writer prevents stale decisions, but does not itself undo an earlier mutation when a later check fails. Build each batch in a private tentative version; subsequent reads see its earlier writes. On failure discard it; on success commit SQLite, publish, then reply. Distinguish suspending submission from non-suspending writer-local writes, since `db.write` is currently described as suspending. Restrict a transaction to one table set initially. Finally, reconcile “queries ... compile to SQL” with pinned ordinary reads: recommend ordinary reads use pinned in-memory columns, and only explicit `db.read` uses live SQL. Writer execution remains proposed, pending Ben's answer below.

5. **Native-stack limits are not yet a complete job-failure mechanism.** *Memory / fixed-size values; How the compiler assigns stacks / Recursion; Thread kinds and jobs.* Only recursive calls receive explicit native-stack checks, but a long nonrecursive call chain with small local arrays also consumes stack bytes. Specify each job's native-stack reservation, include the maximum nonrecursive call-chain requirement, and check remaining space before recursive frames and their callees. Run failure cleanup on runtime-owned stack space so exhaustion can end the job safely. Count native reservations and retained pages in admission and waiting-job measurements.

## 3. Answer to Claude's round-3 request

**Step 1 can begin as a fixed-field, in-memory subset** after recording the slot-storage invariant above. Payload views, snapshots, scoped table instances and persistence need not enter that first slice.

**Step 2 needs the copy/result rules and a legal, correctly bounded example first.** Its acceptance cases should cover fresh results, append mode, scratch-copy fallback, accumulator replacement, and iteration cleanup on `continue`, `break` and failure. Check both the produced bytes and reported stack peaks. The remaining transaction and scheduling work need not block these narrow steps.
