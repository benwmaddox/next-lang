# Sol: few stacks, round 1

The direction is sound for nested construction, but the current text is not an implementable replacement contract. One stack can hold many unfinished values provided only the uppermost one grows physically; lower values wait. Independent growth needs a separate rule. Rewrite the affected M3 task sections before implementation.

1. **Replace the old assignment contract.** DESIGN still requires callee windows above all caller stacks and says two live growing values never share a stack. That contradicts the new example. A window means a function's reserved stack range; replace that model with explicit storage regions (byte ranges), caller-owned destinations, and permission to allocate above a destination on the same stack. Contracts must describe byte requirements and placement when either stack is occupied, including calls through function values. Merely capping the old stack-index arithmetic at two is unsafe. Reprove LLVM's `noalias` promises that pointer arguments cannot overlap.

2. **Append needs two ends and nested rollback.** Distinguish the builder's accepted length from the physical allocation top, which includes temporary bytes. Save lengths, both affected stack tops, and text's byte/code-point counts before producing an append. Publish the new length only after success. For `out += f()` where `f` builds `piece += g()`, each append needs its own checkpoint: an inner success must still disappear if `f` later returns an error. Preserve the original prefix on `Full` and producer errors. Slide only over dead temporaries, using `memmove` (a copy safe when source and destination overlap), after reads/views end. Keep `out += f(out)` on the separate-result path or refuse it. Test nested success followed by outer failure and successful reuse after rollback.

3. **A third growth cannot always be solved by sliding.** Consider three independent builders `a`, `b`, `c`, then append to `a` while `b` and `c` remain needed. Copying onto `a`'s end would overwrite live bytes. Nested construction can instead finish the youngest piece and slide outward; arbitrary interleaving cannot. Specify a safe fallback, such as reserving a builder's full bounded space before placing later values, with that entire reservation counted. Otherwise reject unsupported layouts with a diagnostic in v1. Never silently allocate stack three. Test three nested large producers separately from three interleaved builders, including a call through a function value.

4. **Make 4 KB a compile-time byte policy.** Define it as 4,096 bytes and use the proven upper bound of the bytes actually copied, including UTF-8 expansion. An `Ascii max 1000000` usually containing ten bytes still qualifies unless analysis proves a tighter bound; no runtime placement switch is necessary. A second stack avoids copying only if it holds the obstructing temporary while output is built directly into its destination. Building the output on stack two and copying it back still copies it. Report fallback copies above the threshold. The example's 40,140 payload bytes are conservative; add descriptors (address/length records), alignment and helper storage.

5. **Loops must retain accepted growth.** On every iteration exit, restore temporary storage to the outer builder's *updated* end, not the iteration's original top. Failed appends restore their own checkpoint first. Cover `continue`, `break`, `return`, `?`, nested loops, and copy-down reassignment; measured peaks must stay bounded across many iterations.

6. **Moves transfer cleanup, not physical position.** `take` must keep its byte range alive until the destination dies. A younger moved value cannot survive resetting an enclosing region. Refuse such moves initially; also explain how a moved builder can grow when live values sit above it. Returning a local may require a slide/copy despite transferring ownership. Test a permitted move, a refused escaping move, and later growth.

7. **Native-stack fallback still costs memory.** Large fixed temporaries blocking growth may use the ordinary call stack, but its reservation and admission accounting must include them. Repeated loop allocations must be reclaimed each iteration. Removing fixed scratch must not hide megabyte allocations from bounds or exhaustion checks.

8. **Suspension is compatible with ownership.** Waiting jobs retain their allocated stacks, native frames, provisional output and rollback checkpoints. Synchronise cached tops before waiting; never lend those ranges to another job. Admission (limiting jobs to the memory budget) counts waiting jobs. Cancellation must finish existing I/O/writer cleanup before stack reuse.

9. **Recursion needs renewed accounting later.** Two stack identities do not bound bytes across recursive calls. Retained finished values and large fixed temporaries also accumulate. Require a data-byte/depth budget or forbid retaining such regions across recursive calls; the existing native-stack budget alone is insufficient.

10. **Override notes are insufficient.** Rewrite T13's contracts/runtime/cleanup, T14's placement/moves, T15's nested append/loop protocol, T16's affected fixtures, and T17's accounting/tests. Remove obsolete gap/window assertions and fixed-scratch expectations. Keep the task order; add the cases above. T10 needs no changes.
