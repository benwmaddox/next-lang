# Review 2: `docs/DESIGN.md`

## 1. Round-1 fixes still needing correction

1. **Job failure cannot undo an earlier commit** — *Memory / Stacks; Types / Failures; Thread kinds and jobs.* A job can send a change request, receive the writer's reply, then overflow while constructing its response. The writer may already have published and committed that change. “Its table changes aren't committed” is therefore false. Specify the transaction boundary: recommend atomic writer batches, with failure discarding only uncommitted work. Earlier commits and external effects survive. If whole-job rollback is intended, stage changes until successful completion and define how the job reads its staged writes; see Ben's question below.

2. **Snapshot acquisition and waiting are unsafe as specified** — *Tables across threads; Thread kinds and jobs.* First, loading a root and then incrementing its pin count races with the writer freeing that root. Release ordering alone does not keep memory alive. Specify a safe acquisition protocol; a short runtime lock covering root acquisition/pinning and publication is a concrete initial implementation, without locking row reads. Second, a job can pin an old version, await a writer request, and prevent that writer from proceeding because the snapshot budget is exhausted. Require views to end and the job's pin to be released before waiting for a write; acquire a fresh snapshot afterward. State that this starts a new read phase. Time limits need active cancellation of suspended jobs, not just instruction counting.

3. **The stack call contract is still incomplete** — *N stacks per job; How the compiler assigns stacks.* “Nothing below base” contradicts growing a caller-owned parameter there. Exempt named input/output stacks. State whether the return destination belongs to the called function's window, and exclude its slot from scratch assignment while the result is live. Counting live growing values determines N only if the allocator proves its consecutive call windows always fit; otherwise compute N from the maximum reserved stack index, including destinations and scratch. Include a worked caller/called-function example before implementing step 2.

4. **Mutating “pure” functions are not automatically cacheable** — *Effects and capabilities; Parallel loops.* A no-effect function that appends to a caller's list changes observable state. Reusing its saved return value skips that append. Likewise, purity alone cannot stop parallel chunks from writing a captured caller value. Keep deterministic mutation available, but define cache eligibility separately: read-only inputs, owned result, no caller-visible writes. Parallel bodies may mutate only chunk-owned scratch and their assigned result region. Enforce ownership of each writable argument, not merely the absence of named effects.

5. **The length projections still disagree** — *One declaration, every layer.* SQLite's text `length()` stops at the first U+0000 (zero) character, which is valid UTF-8; it does not always implement the language's code-point limit. Use a generated SQLite function that counts the complete value, or a text refinement that forbids zero characters where built-in `length()` is used. [SQLite documentation](https://www.sqlite.org/lang_corefunc.html#length). Also, a scaled base64 `maxLength` is insufficient: 4,096 and 4,098 bytes both encode to 5,464 characters. Enforce the decoded byte limit and describe the schema length as only a preliminary filter, consistent with the projection-equivalence rule.

## 2. Most important remaining problems

1. **Ids need an instance and partition contract** — *Memory / Typed ids; Frozen tables; Performance model / Layout.* Two file builders of the same node type can both produce slot 0, generation 0. The type cannot distinguish their runtime partitions, and the stated 64 bits have no partition field. Specify frozen ids as a batch-qualified partition number plus local row id, acknowledging the wider representation; reject lookup against another batch. Define equivalent instance identity for multiple ordinary table sets. Keep ordinary ids at 64 bits in v1 rather than promising unspecified smaller encodings that may weaken generation safety.

2. **“Same value twice” is weaker than “no overlapping storage”** — *Memory / References; Keeping it fast.* Passing a record for reading and one of its fields for writing uses different expressions but overlapping memory. Define call checking in terms of their underlying owner and accessed ranges/fields. Reject potentially overlapping arguments whenever either can write or grow, unless disjointness is proved. Emit LLVM's non-overlap promises only from that proof. This rule must precede the optimization work in the first steps.

3. **Failing a job needs an ordered cleanup contract** — *Types / Failures; Parallel loops; Thread kinds and jobs.* Resetting stacks immediately is unsafe if a child chunk or pending I/O still accesses them. Specify: stop scheduling the job, cancel pending operations, wait until children and I/O can no longer access its memory, release pinned roots/builders, discard uncommitted changes, then recycle stacks. Define how suspended jobs reach this cleanup on timeout, and how a chunk failure reaches its parent. This is necessary to make Ben's job-failure decision safe; it does not require per-push `Result` values.

## 3. The disagreement: memory per waiting job

Suspendable jobs remain the decision. “Acceptable for tens of thousands” is not established by the estimate. Assuming 4 KiB pages, 10,000 × 64 KiB is already **625 MiB**, excluding native stacks, snapshot retention, runtime metadata and retained pool pages. At 40,000 jobs, the stated data-stack reservations alone require **156.25 TiB**, exceeding the document's own 128 TiB address-space assumption.

Add a server acceptance workload with a stated waiting-job count, native-stack budget and total memory ceiling. Measure both fresh and previously busy jobs, with old snapshots pinned, and count pooled stack sets against the limits. Bound admission by committed memory and address reservations; define what an excess request receives. The estimate supports testing this design, not claiming its server capacity.

## 4. Question only Ben can answer

- **What must a failed job roll back?** Options: **A**, only its current uncommitted writer batch; **B**, every table change since the job started, requiring staged writes and rules for external effects. **Recommend A**, with explicit transaction batches for operations that must succeed together. Job failure still ends the job under either choice.
