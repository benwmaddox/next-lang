# Review 1: `docs/DESIGN.md`

## Major problems

1. **Memory: “data stays inline” cannot cover variable-length fields.** A text field or nested list has no fixed row size, but tables are arrays of fixed-layout columns and snapshots copy fixed row blocks. Copying a growing value into a row therefore has no specified representation. Store `{byte_offset, byte_length}` (and equivalent child-list ranges) in rows, with payload in immutable table-owned blocks. Define how builders grow/freeze blocks, what a snapshot copies, and what happens at capacity. This adds an indirection and block slack, but keeps ids stable and lets snapshots share unchanged payload.

2. **Threads: the stack assignment needs a call contract.** “Lowest index free” and a hidden base do not say how caller-chosen stacks map to callee parameters, returned growing values, or live values separated by holes. Specializing by base index also does not explain what limits the number of copies. Specify each function’s stack inputs, stack slots it may grow, and output destination; pass an explicit slot map or reserve a contiguous window, and summarize which calls may grow which slots. For `recursive` cycles, forbid growing locals across the recursive call and state a checked maximum native-stack byte/depth budget; a depth count alone does not prevent native stack exhaustion. This replaces the earlier fallback of putting those growing locals on the native stack. The chunk-and-copy fallback for 32-bit/Wasm can move a growing value while a parameter view points into it, so defer those targets or specify movable handles/alias rules and their cost.

3. **Threads: event-loop I/O conflicts with “run to completion.”** A request that waits for I/O either keeps its worker stack live while suspended or must somehow resume after its scope was freed. The design rules out source-level async but gives no continuation model (saved execution state). For v1, make worker jobs non-suspending: keep pending I/O and request state in tables, then schedule another job when the event loop reports completion. If suspension is required, specify an owned continuation and its lifetime.

4. **Tables across threads: publishing the snapshot still visits every block.** Copying an array of all block pointers and counting each block takes work proportional to the whole table, even if one row changed; this contradicts “proportional to blocks changed.” Use a directory tree that shares unchanged branches and copies only paths to changed pages. Give each reader job a pinned root (a top-level snapshot handle that keeps pages alive). Define publication synchronization: the writer finishes initializing pages before readers can access the new root; reclaim old pages after the last reader releases it. State the RAM/backpressure policy for pinned snapshots. Publish all tables in a table set as one version so readers cannot mix versions, and define how it agrees with a SQLite commit or crash recovery.

5. **Parallel loops: input and output lifetimes are missing.** A scoped fork/join (start child jobs and wait for them before leaving scope) can keep `texts` alive in the caller, but “Crossing threads” gives no rule for borrowing that input on workers. Define a read-only pinned input or copy it once for the join. A chunk output on a worker’s stack cannot be read after that scope is freed; put outputs in a join-owned result buffer and finish copying before workers reset their stacks. Specify bounded nested joins or reject nested `parallel for` initially; otherwise workers can all wait for work that nobody can run.

6. **Effects: “pure” does not yet make parallelism or caching safe.** The effect list includes `db.read`, yet parallel bodies may read tables while required to be pure. Also, a function with no named effects could still mutate or grow a reference parameter, and a cached snapshot read is wrong after publication. Define purity as deterministic computation with no externally visible writes, represent snapshot reads as explicit read-only, versioned inputs, and include the version in cache keys. Track read/write/grow effects on parameters; emit `noalias` (LLVM’s promise that pointers do not overlap) only when disjointness is proved.

7. **Refinements: `Int < len(a)` is not a bounds proof.** A negative integer satisfies that condition, so removing an array bounds check is unsound. Require `0 <= i < len(a)` and say when the fact is invalidated by a possible length-changing alias or write. Emit LLVM range/no-alias facts only from proofs the compiler can justify; the current blanket `noalias on stack and arena arrays` is not enough.

8. **One declaration, every layer: length has no shared unit.** UTF-8 byte count, Unicode code points, and HTML’s UTF-16 code units can differ for the same `Text`; SQLite length also has its own semantics. Thus `Text max 80` cannot automatically mean the same limit in storage and a browser. Pick the language’s unit and generate only projections with equivalent semantics; label byte limits separately and make other layers validate explicitly. [SQLite `length`](https://www.sqlite.org/lang_corefunc.html#length) [HTML `maxlength`](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#limiting-user-input-length:-the-maxlength-attribute)

9. **Goals and validation overclaim what the tests establish.** A language cannot ensure every wrong program fails before production; scenarios and mutation scores cover selected cases. Reword correctness as compiler-enforced properties plus measured seeded slips and scenario outcomes. Burin’s measured table reports 0.85× clang `-O2` for DEFLATE; after further sign-analysis improvements, the notes report 0.89×. C itself varied between 34–36 MB/s, and its version rebuilds CRC tables on every call, whereas a fair C baseline would precompute them. The reported workload is Silesia `dickens` (10.2 MB), with one-core medians over nine runs. Reproduce it and set the threshold as throughput ≥0.9× a precomputed-table C implementation; include exact revision, command, machine, memory and compile-time costs. Add a representative standalone tool workload because servers, games and tools have equal priority. [Burin benchmark notes](/D:/code/burin/docs/DESIGN.md:529)

## Shared immutable data across threads

Yes: snapshots can share a syntax tree (AST: the tree of parsed source constructs) once it is copied into table rows. Store nodes in typed columns, child links as typed ids/ranges, and source text as offsets into immutable UTF-8 blocks. A parser may reset its ordinary stack after that copy because the table owns the data. Today, one table-set writer serializes publication and field reads copy values, so large source text or child ranges are inefficient to borrow. Goose shares static read-only data and restricts cross-thread values to flat ones (self-contained bytes without borrowed pointers). [Goose specification](https://github.com/aardappel/goose/blob/master/docs/goose_spec.md)

The smallest addition for efficient readers is a scoped read-only view tied to a pinned root. A checker job acquires one root; functions receive a view as a parameter and may inspect rows or byte/list slices without copying, but may not store or return views. The job releases the root after all joined readers finish; old pages remain alive until then. This needs one pin per job or batch, plus bounds and directory lookups, not per-node atomics. Each checker keeps mutable caches locally. One tree of size S is stored once, plus each worker’s scratch and private caches; overlapping versions retain changed blocks until readers finish.

For parallel parsing, give each file a private single-writer builder. Build directly into table-owned pages or bulk-copy once per file. `freeze` consumes the builder’s mutation authority: those pages and source-byte blocks move into an immutable partition, and the old builder cannot change them. A batch root lists the partitions, with partition-qualified ids. This avoids a serial per-node merge while respecting one writer per table set. Costs include unused page capacity, root/directory metadata, and old versions held while readers pin them. Shared mutation, stack references that outlive a scope, partial publication, per-node reference counting, and unbounded retention remain off the table.

## Smaller issues

- Include generic instantiations and compile-time dependencies in the module-cache key; interface-only hashing can reuse stale code.
- Define how arithmetic, stack exhaustion, recursive depth, and step-budget failures reach callers of functions returning plain `T`.
- Specify the C ABI (shared binary calling rules): enum/record layout, pointer lifetime, error convention, and whether foreign unwinding is forbidden.
- State typed-id table identity, generation width, and wraparound behavior; “stale id is detected (none)” is not a concrete result type.
- Distinguish the `3.5×` four-core parallel-loop target from general workload scaling and report hardware with timings.

## Questions for Ben

- When a data stack reaches its limit, should the operation return a handled `Result` or fail the job? Recommendation: explicit `Result` at operations that can grow, with a process-level fallback only for unrecoverable runtime faults.
- Should v1 promise 32-bit/WebAssembly support with slower chunked stacks, or defer it until 64-bit targets work? Recommendation: name the supported targets up front and defer any target whose stack behavior cannot meet the same safety contract.
- For slow readers pinning old snapshots, should the writer pause writes at a memory budget, or should the runtime cooperatively cancel and restart slow jobs? Recommendation: pause writes; never invalidate a live view.
