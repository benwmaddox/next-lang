## 1. Example and host contracts

1. **The chat page leaves absence and query consistency undefined** (lines 41–56; Databases lines 265, 269–270). `Room.get(id)` returns `Option` (a value that may be missing) by the database rules, so `r.name` is invalid unless absence is handled. If `not_found()` means 404, define it as immediately exiting the page with a 404 response; otherwise the fallback cannot be a `Room`. Likewise, `online.who.get(id)` may be absent and needs a defined empty-set/default-count path. The two `db.read` blocks may suspend separately and see different commits. Read both queries in one transaction. Define `newest(50)` ordering, e.g. descending immutable `Message.Key`, so pagination and results are reproducible.

2. **The action, tests, and route wiring are not a complete typed example** (lines 64–84). `PostError` and `Viewer` are undefined; define their cases and the viewer’s bounded `name`. `Message.add` can fail (for example, `Full`), so show the error conversion; show `ok(())` after signaling. Handle `env.open`, `env.http` binding, and query failures explicitly as startup or request errors. The test should bind `Db.memory(Chat)`, handle/unwrap the setup transaction, and compare the action result with `ok(())`. Since name resolution is unspecified, name the local key `room_key` to keep it distinct from the page `room` called on line 75. Show how `main` binds the route’s path key and injects a trusted `Viewer` and `Db<Chat>`; neither belongs in user-controlled form fields. The action’s effects include database write and live signal, and the page reads a shared snapshot, so “read and write only Chat” (line 87) is false. Add the signal capability/effect and route grants to the manifest.

3. **The “one declaration” form claim is not met** (lines 43, 59, 64; One declaration lines 513, 528). The body limit is repeated as `Text max 2000`, while `Message.body` is another declaration. Use one named field type for both. A browser’s `maxlength` counts UTF-16 units, not Unicode code points; generate a code-point counter/check as the projection rules already require. Keep `Viewer` server-injected, not a posted author value. Escaping a URL attribute does not reject dangerous schemes such as `javascript:`; validate URL values or use a restricted URL type.

4. **A live refresh can render stale data and lose an update** (lines 52, 55–57, 67–68). The live list captures `recent` from the original request’s stack; re-running that renderer with the captured list shows the same rows. Make refresh load current rows from the room key in a new bounded `db.read`, then pass owned rows to a renderer that only formats its inputs; no stack view (temporary reference) or snapshot pin (hold on an immutable version) may survive the wait. A database commit can succeed before `signal` is sent, leaving clients stale. Specify delivery and recovery: preferably numbered refresh notices, combining repeats and reloading after reconnect; if delivery must be guaranteed, store pending notices in the same database transaction. Bound each open page’s event queue and any cached HTML; render output bounds must include escaping and markup, not just input rows. Enforce request byte limits before decoding bounded text.

5. **The game host needs scheduling and failure rules** (lines 615–619; Threads lines 282–305; Memory lines 186–188). Program globals have one home worker, so serialize tick and draw there; otherwise draw may race a tick or access a non-shared global from another worker. Treat draw as an entry point (a function the host starts) with its own stack reservation (reserved temporary memory). State that tick cannot suspend; if it can, specify how the host prevents another tick or draw from observing a partially updated state. A failed tick currently may leave earlier writes in place; choose whether to stop the game or stage a tick and publish it atomically. The bounded frame draw list needs a capacity source and a full-buffer outcome, separately from simulation state. Do not let draw consume the simulation random-number generator (RNG), or render frequency may change the random sequence of later ticks. Include its current state in saves, too. Keep frozen asset pools alive for the host’s full run; their normal lifetime is the creating scope.

## 2. Numbers and package details

- **Fast floats and replay** (lines 470–472, 619): a fast result may be NaN, but plain `Float` forbids it. Type fast-block temporaries/results as `FloatNaN` and check conversion back. The strongest LLVM fast-math permissions (reordering arithmetic and assuming no NaN or infinity) conflict with `FloatNaN` and allowed infinities; specify which permissions can be used. Specify whether the promised NaN and infinity behavior of `FloatNaN` overrides the general divide-by-zero rule in Failures (line 454). A fast result written into tick state cannot simply be “excluded from replay checks”: the state hash includes it and it may affect later ticks. Keep fast values out of replay-checked state/control or define an explicit comparison rule.

- **Integer width and fixed-point operations** (lines 467–469, 473): distinguish logical arithmetic width from packed field width. `Int 0..1000` may occupy 16 bits in state, but its shift and overflow rules remain those of 64-bit `Int`; `UInt64` must retain unsigned 64-bit arithmetic semantics. Specify shifts as `0 <= n < width` (a shift by width fails), and define signed minimum divided by −1. For `Fixed<2>`, specify product/division scaling and intermediate width; e.g. 1.23 × 1.23 is not an exact number of hundredths. Require exact results or an explicit rounding mode/conversion.

- **Package cache keys** (lines 596–598, Development experience line 581): every file sees private declarations across its package, while the build caches one object per module. Define whether a module is a file or package. If files compile separately, changing a private sibling declaration or a callee’s computed stack requirements must invalidate callers that depend on it; preserve generic-source and compile-time-read inputs in the key as line 581 requires.
