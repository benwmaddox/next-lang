# Round 16: `docs/DESIGN.md`

## 1. Main findings

1. **Middle-end choices and performance are target-dependent** (`DESIGN.md:612–616`). LLVM shares passes, but inlining and vectorization consult target feature and cost information, so “the middle stage works the same” is too absolute ([`TargetTransformInfo`](https://llvm.org/doxygen/classllvm_1_1TargetTransformInfo.html)). The 1.5–3× baseline loss and 10–20% PGO gain (optimization guided by recorded runs) have no named CPU, workload, or toolchain and are not general; a higher instruction-set level can lose on memory-bound or frequency-sensitive code. Replace estimates with measurements for named game, server, and tool workloads.

2. **x86-64 levels are feature bundles, not release dates** (`:614`). `x86-64-v3` includes AVX2 and FMA (fused multiply-add: one rounding instead of two) plus other extensions; Haswell supported it in 2013, while some newer CPUs still lack it. `v4` specifies a particular AVX-512 subset, not every AVX-512 extension. Name the bundle rather than dating it, and say the launcher checks every required feature ([Clang x86 targets](https://clang.llvm.org/docs/UsersManual.html#x86)).

3. **CPU features do not define a platform target** (`:614`). Portability across Windows, Linux, macOS, and Android also depends on the ABI (binary calling and data-layout rules), executable format, system libraries, and minimum OS versions. macOS arm64’s baseline is M1 class, while Android `arm64-v8a` starts at Armv8.0-A with Neon vectors and floating point/FMA; `armv8.2-a` is not its universal baseline. Android `x86_64` requires v2. State these separately, and build separate macOS x86-64 and arm64 slices if both are supported ([Clang AArch64 defaults](https://github.com/llvm/llvm-project/blob/main/clang/lib/Driver/ToolChains/Arch/AArch64.cpp), [Android ABIs](https://developer.android.com/ndk/guides/abis)).

4. **`native` means the build host, not each developer’s eventual machine** (`:614, 627`). A binary produced on one developer’s CPU or a remote builder may require features absent from another’s laptop. Keep `native` for local runs; require an explicit deployment target for shared artifacts and cross-builds. Put the resolved feature set, target OS/ABI, compiler version, and flags in build-cache and artifact identity so a host change cannot reuse incompatible objects.

5. **The startup check and function dispatch need a baseline-safe contract** (`:614–615`). Keep startup code, dependency initialization, dispatcher, and refusal path baseline-safe; ensure LTO (optimization across modules) cannot introduce specialized instructions before the check. On x86, check CPU features (CPUID) and OS support for saving vector registers (OSXSAVE/XGETBV). On Linux/Android ARM, query HWCAP (OS-advertised usable features) rather than guessing from a CPU name ([LLVM CPU detection](https://github.com/llvm/llvm-project/blob/main/compiler-rt/lib/builtins/cpu_model/x86.c), [Android CPU features](https://developer.android.com/ndk/guides/cpu-features)). For virtual machines and heterogeneous cores, use features safe on every eligible core.

6. **Do not imply one LLVM multiversion resolver works on every platform** (`:615`). Function cloning and automatic resolution depend on compiler, linker, and object-format support; document tested combinations for Windows PE, Linux/Android ELF, and macOS Mach-O. A baseline function-pointer dispatcher is a fallback. Keep the call boundary’s ABI stable across clones, and let tests and benchmarks force each variant ([Clang `target_clones`](https://clang.llvm.org/docs/AttributeReference.html#target-clones)).

7. **Profiles and BOLT need a reproducible, platform-scoped workflow** (`:616`). A profile alone does not reproduce a build: explain collection, merging, selection, and stale-profile rejection; key profiles with source, compiler, flags, dependencies, and workload identity. Measure PGO gains on that workload. BOLT’s documented scope is primarily x86-64/AArch64 ELF; describe it as a later Linux-server option, not a general Windows/macOS step ([BOLT README](https://github.com/llvm/llvm-project/blob/main/bolt/README.md)).

8. **The exact-float promise needs explicit lowering and a narrower domain** (`:504, 621, 666`). LLVM IR (compiler intermediate code) without fast-math flags guarantees bit-identical core-operation results across machines and optimization levels for non-NaNs under its default environment: round-to-nearest, traps disabled, status flags unobserved, subnormals preserved ([LLVM LangRef](https://llvm.org/docs/LangRef.html#floating-point-semantics)). Clang’s default precise mode enables `-ffp-contract=on`, so “without fast-math” does not prohibit FMA; disable contraction and reassociation for all exact code ([Clang FP model](https://clang.llvm.org/docs/UsersManual.html#cmdoption-ffp-model)). Vector reductions (combining elements into one sum) must retain addition order; LLVM supports ordered versions on some targets, with limited speedups ([LLVM reductions](https://llvm.org/docs/Vectorizers.html#reductions)). Fix and restore the floating-point environment around foreign calls; specify NaN payload policy. Matching results need not mean identical instructions.

9. **Exclude `sin` and `exp` unless their implementation is fixed** (`:504, 621, 666`). They may remain library calls, become LLVM built-ins, or use a selected vector math library; libc may also dispatch by CPU (glibc `sin` has a runtime selector). Pin a deterministic scalar/vector implementation and dispatch policy, include runtime identity in replay metadata, or narrow the equality guarantee for these functions ([LLVM vector math](https://llvm.org/docs/Vectorizers.html#vectorization-of-function-calls), [glibc `sin` dispatch](https://github.com/bminor/glibc/blob/master/sysdeps/x86_64/fpu/multiarch/s_sin.c)).

## 2. Smaller issue

The JIT comparison (`:619`) understates runtime opportunities: loop lengths, alignment, startup configuration, and branch behavior still vary with static types. AOT can add guarded fast paths; a JIT can adapt them. Remove “small, rare loss” unless measured, and say which values the first implementation specializes.
