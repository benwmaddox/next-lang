# Review 3: `docs/DESIGN.md`

## 1. Round-2 fixes that remain incomplete

1. **Loop cleanup can erase the result.** *How the compiler assigns stacks; Loops can't quietly fill a stack.* `render` builds `out` on destination stack D, then says each iteration resets stack tops. Resetting D discards the appended bytes; excluding it leaves the rule incomplete. Carry D's updated top across iterations and reset only iteration-local scratch. `acc = merge(acc, x)` also peaks at old `acc` plus the new scratch result. Reserve and report that transient peak; “largest value” describes only the final live state.

2. **The result destination needs two distinct contracts.** *How the compiler assigns stacks; References.* A fresh `Text` result belongs to the caller; appending to live `out` is different. The explanation treats the result suffix as part of `out` without specifying when ownership transfers or how the hidden destination participates in owner/range overlap checks. Define that append contract as in Section 3, or build on a scratch stack and copy, dropping the no-copy claim.

3. **A parallel join cannot use the ordinary no-pin-across-wait rule.** *Thread kinds and jobs; Parallel loops; Tables across threads.* Chunks read the caller's snapshot while its job waits at the join. Keep a structured pin to that captured root until all chunks stop, and budget its retention. If chunks pin individually, each must safely pin that same root before the parent releases it, not acquire a newer root. Also mark `db.write` as suspending: workers wait for the writer's reply. Define `may_suspend` across all calls separately from external I/O effects.

4. **Deadlines need checks in counted loops too.** *Keeping it fast; Loops can't quietly fill a stack; Thread kinds and jobs.* Finite loops omit step budgets, but cancellation is checked at those checks. A huge finite loop could hold a snapshot past its deadline. Keep periodic time/cancellation polls in long loops while omitting only the termination budget. State that an uncancellable foreign call can delay timeout handling.

## 2. Most important remaining issues

1. **Specify the stack layout for nested growing values before step 2.** *Memory; How the compiler assigns stacks; First steps.* The table layout gives a `Text` field `{offset, length}`, but says nothing about `List<Text>` or records with multiple variable-size fields on a stack. For step 2, explicitly reject nested growing containers. When added, use separate compiler-assigned stacks for list descriptors (offset/length records) and payload (child bytes), store offsets rather than borrowed pointers, freeze children once inserted, and edit them by rebuilding/copying. Include each stack, alignment, and temporary copy in the bound; one memory block does not support arbitrary in-place nested growth.

2. **Atomic batches do not say where transaction decisions read.** *Transactions; Tables across threads; Effects and capabilities.* Two jobs can read the same snapshot showing one item in stock, each decide to sell it, and each send an individually atomic “set stock to zero” batch. Both sales succeed. Run the transaction's check and writes at the writer against its latest version, or define version-checked writes that reject/retry a stale decision. The transaction must not suspend while it holds that decision state. Also clarify whether `db.read` sees the latest committed SQLite state while table reads see a pinned snapshot, and which one a transaction uses. Define batch states and the failure race: cancel a queued batch; if the writer is applying it, require the writer to abort or finish and acknowledge before job cleanup releases buffers; a committed batch stays committed.

3. **Frozen batches need a runtime identity before parallel builders create ids.** *Frozen tables; Memory / Typed ids.* The spelling `b.Node.Id` only prevents mixing batches if `b` is a unique batch token, not a reusable variable name, and partition numbers are reserved consistently. Create a scoped batch token first; builders inherit it and receive distinct partition numbers before publishing. Cross-file references to not-yet-frozen rows need a fixup step (a later pass that resolves temporary references) or preassigned handles. Explain that ids cannot escape the batch scope.

4. **Singleton table sets conflict with private per-job caches.** *Memory / Typed ids; Frozen tables.* Ordinary table types name one program-wide set, while each checking job is said to keep its own mutable cache tables. Distinguish singleton published sets from scoped job-owned cache instances; give cache ids an owner scope so they cannot escape the job or be mixed across jobs.

5. **Payload reclamation needs root ownership, not only reader pins.** *Memory; Tables across threads.* “Freed when no job pins it” is wrong for blocks still reachable from the current root, even with zero readers. Give roots/tree edges writer-side references; when a pinned old root is released, drop its edges and reclaim shared nodes or payload blocks only when no live root points to them. Compaction must rewrite descriptors in a new version and retain old bytes for older roots. Finding every reference may scan the table, so budget that maintenance separately or defer it. This needs root/block references, not per-row reader counts.

## 3. Answers to Claude's round-2 questions

**Are the loop rules workable for ordinary code?** Yes for bounded collection and formatting loops when bounds flow from inputs. But `rows: List<Row> max 500` and `name: Text max 80` do not imply 40,000 output code points: `line` adds punctuation and a count. Bound the whole produced piece (for example, `line(r): Text max 80`, including separators and count, with helper outputs respecting that contract); then 500 rows imply `out: Text max 40000`. The current `render(rows)` lacks these bounds, so it fails the rule as written. Stack reservation is in bytes: 40,000 code points can take 160,000 UTF-8 bytes, before headers and alignment. For source tools, define a bounded corpus or project batch size and a resident-tree budget; a default reservation followed by job failure is not a useful input contract.

**Is “out's growth area” sound?** Conditionally. Treat `out` as one exclusive builder; `line` receives exclusive permission to append, writes a suffix, and returns its length, not a second owned `Text`. Pass the remaining capacity so a checked append cannot write past the maximum before failing. On success the caller advances the builder's logical end; on failure restore both its previous logical end and stack top. Check that `r` and the output builder have disjoint owners/ranges. The iteration scope then preserves the builder's new top and resets only scratch. With bounded `rows` and `r.name`, N = 2 is plausible if `upper` and formatting helpers use only stack 1 for scratch and the output builder D for results; state that in their contracts. Otherwise use a scratch result and copy.
