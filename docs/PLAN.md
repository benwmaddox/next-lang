# Implementation plan

Started 2026-10-24, after the design rounds in DESIGN.md converged. Ben's decisions for the build: the compiler is written in **Rust**; it emits **LLVM IR as text** (as Burin's helper compiler does) and builds it with **clang**; development and tests run on **Linux (WSL)** first, Windows later.

## Roles

- **Claude** (manager and reviewer): writes each task (docs/tasks/T*.md) with its acceptance tests, reviews the diff and the test run, asks for fixes, commits and pushes. Keeps DESIGN.md and this plan current.
- **Codex, `gpt-6-luna`, reasoning `max`** (implementer): implements one task at a time in this repository. Never commits, never creates or switches branches. Ends each task with a short report (docs/tasks/T*-report.md): what it built, how to run it, what's left, and any place it had to choose something the task didn't say.
- **Codex, `gpt-6.1-sol`, reasoning `high`** (peer): reviews plans and tasks before they go to Luna, and is asked when a design question comes up during the build.

## Layout

```
Cargo.toml              workspace
compiler/               the `nlc` compiler (Rust): lexer, parser, checker, LLVM IR emitter, driver
runtime/                the small runtime the generated code links against (C, compiled by clang)
tests/                  language tests: one directory per program, with expected output
docs/                   DESIGN.md, EXAMPLES.md, PLAN.md, tasks/, reviews/
```

Commands (in WSL; Codex itself runs inside WSL, with its own settings in `~/.codex-nl` and the binary in `~/.local/codex-nl`): `cargo build`, `cargo test` (the compiler's own tests and the language tests), and `nlc run <dir>` / `nlc test <dir>` on a package directory. The Cargo target directory lives in the WSL home (`CARGO_TARGET_DIR=~/.cache/next-lang/target`), not on the Windows drive, so builds stay fast.

## Order of work

This is the one queue; no other part of this plan sets a different order. Each entry is described below.

1. **O1** (done): the offset runtime and slice ported onto main, and inline stack allocation (docs/tasks/O1-offset-runtime-and-inline-alloc.md).
2. **H1** (done): the self-hosted front end, selectable, with Rust still the default (docs/tasks/H1-selfhost-frontend.md). Its child is built in pointer mode until O6 (a build setting, not a pointer-only feature).
3. **Two compilers, split (Ben, 2026-10-25):** Rust nlc is stage 0 and the reference; the self-hosted compiler (selfhost/) is its own implementation. They share only the language (DESIGN.md), the C runtime and the test suite, and are compared by behaviour. Until the self-hosted compiler builds the whole suite, features land in Rust nlc first and the E-track catches up; after that, new features land in the self-hosted compiler and Rust nlc is frozen except for fixes needed to keep building it. So H1 stays as it is (a working, optional front end; Rust the default), and H1b's speed work and H1c are dropped; only H1b's input-policy part remains, as a small task: one set of package limits for every command (docs/tasks/H1b-frontend-speed-and-policy.md, item 1), which the self-hosted compiler follows too.
4. **R1** (done), **runtime without per-operation heap use, with buffered standard output and `match` on `byte`** (docs/tasks/R1-runtime-arena-only.md): file reads, listings and the job context stop using `malloc`/`calloc`/`realloc`/`strdup`; stdout and stderr buffered.
5. **E-track, the self-hosted compiler end to end (Ben, 2026-10-25; starts now):** E1 builds every stage in next-lang for a small subset (docs/tasks/E1-selfhost-end-to-end-slice.md): checker and code generator after the existing lexer and parser, LLVM IR built by clang, linked for now with the C runtime, judged by identical stdout, stderr and exit status against Rust nlc on every package the subset accepts. **E1c, right after E1 (the standard library needs no C library, DESIGN.md):** a design note reviewed by Sol (the `sys` operations, core-library-only use, the `_start` entry, freestanding memory functions, the native stack), then the self-hosted compiler builds its programs with a next-lang core library instead of the C runtime (freestanding, since E1's programs link no foreign libraries) for E1's subset (entry, buffered output and flush, integer formatting, failure messages and statuses, test mode with `NLC_TEST_INDEX`), with the comparison against Rust nlc unchanged. The core library's file I/O (reads straight into the destination, writes, the atomic write and the streaming file writer from DESIGN.md) follows when a later E-task needs files, and the streaming writer is how the self-hosted compiler writes large IR; from then on, every runtime and standard-library need of the self-hosted compiler is written in next-lang, never in C (programs may still link external libraries through foreign bindings). E2 adds structs, enums, `match`, `Option`/`Result`, `?`; E3 arrays, lists, `Ascii`/`Text`/`Bytes` and builders; E4 refinements and the remaining collections; then the rest, until the self-hosted compiler builds itself. The E-track replaces the hybrid steps (H1b speed, H1c, H2 onwards): the hybrid track ends at H1, and the self-hosted checker and code generator are built as one next-lang pipeline compared with Rust nlc by behaviour.
6. **O2, O3, O4,** in order.
7. **L1** nested layout flattening (after O4, keeping O4's element-reference form).
8. **O5, O6, O7,** ending with offsets as the only mode.
9. **Floats** (after O7, so new number paths are built for offsets only).
10. **O8** (optional): a separately measured proposal for 32-bit offsets, adopted only by its own decision.
11. **M4 onwards** (DESIGN.md's first steps 3 to 7).

The small fixes listed below go into whichever of these tasks touches the same code, or into a task of their own between them. Not yet placed (each needs a decision on where it goes): the scheduler milestone (pooling, trimming, clearing, admission, and the pinning rule for asynchronous I/O buffers), Windows support, `strict_stack`, string-literal patterns, and the S1 parallel-tool validation.

## Milestones

Each is small enough to review in one sitting, ends with passing tests, and maps to DESIGN.md's first steps. The finished ones are in Done; this records what each covered and what it left for later.

- **M0 Pipeline:** the whole path from source to a native program, with a typed representation between the checker and the emitter, functions, scalars, checked arithmetic and casts, `if`, calls, `print` and build errors; `for` loops over `..` and `..=` ranges with `break`/`continue`; `test` blocks with `nlc test`.
- **M1 Values,** under the refinement contract (DESIGN.md, "The refinement contract": prove it or write a cast): `enum` with payloads and exhaustive `match`; `Option` and `Result`, where `?` propagates an `Option` or a `Result` under its function's return type, and `?.` and `??` (including `?? return/continue/break`) work on `Option` only; `struct` with field defaults and initialisers; named refinements and range refinements on integers (`wrap` and `clamp`); `const` with compile-time evaluation.
- **M2 State and ids (DESIGN step 1, fixed-size part):** fixed arrays, `list`, `pool` with generation-checked ids, as locals and in a small `global`; structure-of-arrays layout; `Full` as a `Result`, `discard`; writable loop views and the no-removal-while-viewing rule. Left for later: nested collections are stored inline per enclosing element, not flattened (L1, below).
- **M3 Data stacks (DESIGN step 2):** growing values (`Ascii`, `Text`, `Bytes`) on the data stack: stack contracts, fresh-result and append modes, iteration scopes, bounds per entry point, `inspect stacks`. It completed the sequential step 2 cases assigned to it. Left for later: reusing stacks across jobs and job cleanup (the scheduler milestone), rendering from shared snapshots (with `shared global`), copying, resetting and returning pools (DESIGN.md "Later"), and bounded file writers that flush in chunks (the effects step).
- **Offset addressing milestone (decided 2026-10-25, built on X1):** data-stack references become offsets (DESIGN.md "The job's data stack"). The gate passed in X1 round 3: with the base cached, tight loops are within noise of pointer mode (about 675 ms both ways on a 100x longer run). O1 to O5 keep the whole suite passing in pointer mode and grow a poison-verified offset corpus (`NLC_STACK_VERIFY`); an offset path not yet supported fails closed with a build error and is listed for the next O-task that covers it. Offsets are 64 bits throughout O1 to O7.
  - **O1:** port the spike's runtime (base in the context, `mremap` growth, guard page, `NLC_STACK_VERIFY`), its `NLC_STACK_MODE` switch and its supported slice by hand onto current main, adapting them to T29, T31 and T32; do not merge the spike branch `spike/offset-stack`. Also make region allocation an inline bump of the cached top, with an out-of-line call only to grow (`nl_stack_alloc` and `nl_context_set_top` are runtime calls today, about 17% of the self-hosted parser's profile in T32's measurements).
  - **O2:** descriptors and builders (`Ascii`, `Text`, `Bytes`) as offsets; and write the cached top back with a plain store into the job context instead of the out-of-line `nl_context_set_top` call (9% of the self-hosted parser's profile after O1).
  - **O3:** parameters, hidden result destinations and function values as offsets. With O4, it retires the raw-pointer call paths, including the large-value paths that pass by address today (and the "must travel by address" comment in compiler/src/emit.rs near the lazy-collection size code, which becomes "by offset").
  - **O4:** collections, views and element references: an element passed as its collection's offset plus an index, read in place through its lanes, replacing T13's gather into contiguous scratch and scatter back, with its accounting, `inspect stacks` output and tests updated.
  - **O5:** runtime I/O and foreign calls with pinning. Bytes is the one byte-buffer I/O form: O5 migrates the fixtures that read files into `list<byte, N>` (T20's form) to `Bytes` and removes that overload (the `list<byte, N>` branch where compiler/src/emit.rs chooses between `nl_fs_read` and `nl_fs_read_string`, and `nl_fs_read` in runtime/nl_runtime.c).
  - **O6:** the self-hosted lexer and parser compile and run in offset mode, with the selfhost comparison passing, also under `NLC_STACK_VERIFY`; full offset coverage of the suite.
  - **O7:** once the whole suite passes in offset mode, including O6's selfhost comparison, make offsets the default and delete pointer mode: the `NLC_STACK_MODE` switch, the pointer ABI, allocators and top/base access in compiler/src/driver.rs, emit.rs and runtime/nl_runtime.c, pointer-only analysis and report helpers, and their tests; H1's pointer-mode bootstrap exception goes with them. Add the cap as a growth limit (DESIGN.md "Growth limit (the cap)"): `stack_reserve` per entry point in `package.toml` (64 GiB default, binary units); `data stack range exhausted` through `nl_fail` past it (exit 1; 70 in a test child), never a crash; a build warning for a computed worst case above the cap (naming the entry point, the cap, the bound and the critical path) and one for each single region larger than the cap; `inspect stacks` showing the uncapped bound and the cap, with `stack_peak` keeping uncapped bounds; arithmetic overflow in the bound analysis diagnosed, never wrapped; growth refused by strict overcommit (`vm.overcommit_memory = 2`) failing the job like the cap. Tests at the cap's N and N+1 pages, an unknown-bound entry point growing to the cap, and the self-hosted parser under the default cap and under one just above its measured peak.
  - **O8 (optional, after O7):** 32-bit offsets scaled by 8, only as a separately measured proposal: it must state alignment, how its 32 GiB range fits the 64 GiB default cap (a rule for choosing 64-bit offsets), and overflow checks, and is adopted only by its own decision. X1 did not measure it.
- **One approach at a time (Ben, 2026-10-25):** the offset design in DESIGN.md is the only data-stack design. Pointer mode survives only until O7 removes it, and after O1 no feature is built for pointer mode alone (every new emitter path works in offset mode, or fails closed there and is listed for the next O-task). T28 (a capped up-front reservation) is cancelled: O7 adds the cap as a growth limit. The spike branch `spike/offset-stack` and its worktree are retired once O1 lands (the branch stays on GitHub as the record; the worktree is removed). Front ends: the Rust parser and the self-hosted parser must keep matching byte for byte (the comparison runs in `cargo test`), so they can't drift; how H1 and the later default switch use them is in "Hybrid track". When a decision replaces an earlier one, the earlier text is rewritten, not left alongside.
- **Scheduler milestone (with the job scheduler, after M3; not yet placed):** per-worker stack pools, per-entry-point demand histories, trimming, `clear_stacks_between_jobs` and admission, as DESIGN.md "The job's data stack" describes. It first adds per-job accounting of written and committed pages, kept apart from the allocation high-water mark, before any history is used for trimming or admission. Waiting jobs keep their regions, provisional bytes, checkpoints and native frames; admission counts waiting jobs; cancellation finishes I/O and writer cleanup before a job's stack is reused; per-job native stacks and switching (T17 reports the native bound only; T19's recursion checks run on the one native stack).
- **Windows support (not yet placed):** `MEM_RESERVE` and commit in 64 KB chunks wherever a range is first written, stack moves that copy only committed chunks, `VirtualLock`, and the startup checks of DESIGN.md "Static allocation".
- **`strict_stack` (not yet placed):** start an entry point's stack at its full computed worst case, committed at startup, refusing to start if it doesn't fit; an unknown bound or a bound past the cap is a build error; with the scheduler, the declared number of strict stacks provisioned at startup; `prefault` and `locked` for them.
- **`Text` trusts its invariant (small, Rust nlc and the self-hosted compiler alike):** remove the re-validation in compiler/src/emit.rs `emit_text_to_data` (it runs `nl_utf8_count` over text built from already-valid pieces; sum the pieces' code-point counts instead) and make code-point offsets for slicing (`nl_utf8_offset`, used by `emit_string_slice_to`) count lead bytes without validating; keep validation only at the boundaries DESIGN.md lists; add a test-build-only assertion that re-validates every constructed `Text`, so a bug that produces invalid `Text` is caught by the suite; measure a Text-heavy benchmark before and after.
- **Buffered standard output and `match` on `byte`:** part of R1 (docs/tasks/R1-runtime-arena-only.md).
- **Floats:** `double` and `float` per DESIGN.md "Floats" and "Deterministic by default" (no NaN in plain floats, `double nan`, `fast { }`, the language's own `sin`/`exp`, no fast-math by default), then `str_fixed(x, digits)` (EXAMPLES.md's logsum `percent` needs it).
- **L1, nested layout flattening (after O4, before M4):** flatten nested collections into one lane per field across all enclosing elements, as DESIGN.md's Layout section says (T06 stores each nested collection's lanes inline per element; see docs/reviews/claude-T06-review.md), with a benchmark of a loop over all nested items. It changes only how nested lanes are laid out: element references keep O4's form (collection offset plus index), so there is still one way to pass an element. It also audits the size rules shared by the checker's sizing and the emitter's `type_size` and `type_size_legacy` (compiler/src/emit.rs), renaming them for the representations they size (inline storage versus collection and descriptor layout) so the checked and emitted sizes keep agreeing.
- **Optional convenience: string-literal patterns** in `match` over `Ascii`/`Text`/`Bytes` (`match word { "fn" => ..., "let" => ..., _ => ... }`), compiled to length-then-bytes comparisons; S1 works without it.
- **M4 onwards** follow DESIGN.md's first steps 3 to 7 (refinements as LLVM facts, measured on DEFLATE; `check fast == reference`; effects; builders, `freeze` and parallel loops), each planned when the one before is done.

## Small fixes

Each names the code and the fix; none changes a design decision.

- **`??` in Result diagnostics:** compiler/src/checker.rs, the unused-Result and Full-operation messages (at lines 3712, 3714, 4491, 4493, 4539, 4541, 5100 and 5102 today) say "handle it with '?', 'match', or '??' where supported", but `??` is rejected on every `Result`. Change them to "handle it with '?' or 'match'", keeping "or write 'discard' when dropping Full is intended" only on the built-in Full operations `discard` accepts, and update the diagnostic snapshots.
- **Stack hook reports a resident sample, not touched pages:** runtime/nl_runtime.c, the `NLC_TEST_BUILD` exit report read through `NLC_TEST_REPORT_STACK_TOUCHED`, counts `mincore`-resident pages and prints `touched=`. Rename the variable to `NLC_TEST_REPORT_STACK_RESIDENT` and the field to `resident=`, keep `peak_used` as the allocation high-water mark, and update compiler/tests/inline_text.rs and compiler/tests/stack_contracts.rs. It is a test hook, not the scheduler's demand measure.
- **Reject stack settings that aren't implemented:** compiler/src/driver.rs, the `package.toml` key loop (the `continue` for keys other than `job_headroom`, `globals_budget` and `recursion_budget`), silently ignores unknown keys. Make `strict_stack`, `clear_stacks_between_jobs`, trimming settings and `stack_reserve` build errors saying they aren't implemented yet, each until its task lands (`stack_reserve` in O7).

## Rules for every task

- Tests first-class: every feature lands with language tests (a program and its expected output, or a `test` block), and every error the compiler reports lands with a test that triggers it.
- Error messages name the line and say what to do, as DESIGN.md's Development experience asks.
- No dependency on Burin; code may be copied from it (D:\code\burin, Apache 2.0) with a note in the file.
- No new external Rust crates without saying why in the report.
- Keep it simple: no optimisation passes of our own; LLVM does that.

## Self-hosting track (decided 2026-10-24)

Ben adopted the recommendation both reviews reached (docs/reviews/claude-selfhost.md, docs/reviews/sol-selfhost-r1.md): self-host the compiler in stages, starting after M3, as DESIGN.md's planned "parallel tool" validation program. The Rust `nlc` stays the reference throughout.

- **S0 (done):** the prerequisites S1 needs that don't depend on M3: T19, T20 and T21 (see Done).
- **S1a (done):** the lexer and parser in next-lang, sequential, matching `nlc lex` and `nlc parse` byte for byte, including diagnostics; the comparison runs in `cargo test`.
- **S1, the parallel-tool validation (not yet placed):** the same lexer and parser parsing every package under `tests/` in parallel into frozen pools, matching the Rust parser's trees and diagnostics exactly, measured against the Rust parser. It is the validation plan's parallel-tool program and waits for builders, frozen pools and parallel loops (DESIGN step 6). It is separate from H1, which uses the sequential S1a parser.
- **Hybrid track (decided 2026-10-25, Ben):** `nlc` starts using self-hosted pieces as soon as each matches Rust, moving more of the pipeline to next-lang step by step instead of waiting for a whole self-hosted compiler. Each piece needs a fixed format for its output and a both-ways comparison over the whole suite. For H1, the Rust front end stays the default; switching production parsing is a separate, recorded decision after H1's report, and after it the Rust parser stays selectable as the comparison reference, with no automatic production fallback. How later pieces switch is decided with each.
  - **H1, the front end** (docs/tasks/H1-selfhost-frontend.md): a compact binary tree format holding exactly what `ast.rs` holds, with every field mapped explicitly; the self-hosted parser writes it to stdout; `nlc --frontend=selfhost|rust` reads it back into `ast.rs` and continues with the Rust checker and emitter; the self-hosted front end is built through an internal Rust-only path and cached by its sorted source paths and contents, manifest, the nlc build identity, runtime content, target, optimisation level, stack mode, toolchain and wire version, with a lock and atomic publication; every run and test fixture runs both ways with identical output and diagnostics. Rust stays the default in H1. A process boundary first; linking the self-hosted code into nlc waits for C-callable exports.
  - **H1b speed work, H1c and H2 onward: replaced by the E-track** (2026-10-25, compilers split). The hybrid track ends at H1; the self-hosted checker and code generator are built as one next-lang pipeline and compared with Rust nlc by behaviour (Order of work, item 5), not fed piece by piece into the Rust checker.
- **S2: the checker** (built through the E-track), compared with Rust nlc by first error (message and position) on invalid programs and by behaviour of the built executables.
- **S3: code generation** (built through the E-track), compared by behaviour on every test program at development and release optimisation levels.
- **Bootstrapping, at S3:** the pinned Rust `nlc` (stage 0) builds the next-lang compiler (stage 1), which builds stage 2, which builds stage 3; stages 2 and 3 must be byte-identical (fixed clang, runtime, target, flags, paths, no timestamps, no hash-order output). Identical stages show stability, not correctness, so the cross-compiler comparison on valid, invalid, generated and limit-boundary inputs stays.
- **Retiring the Rust compiler** is a later decision, only after the validation programs pass and the next-lang compiler has proved cheaper to maintain.
